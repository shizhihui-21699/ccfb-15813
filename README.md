# 票房异常监管识别系统

基于**售票记录 + 排片数据 + 结算上报 + 线上销售**，识别两类票房违规：

- **虚假票房（刷票房）**：幽灵场、锁场、低价票刷量、片方自购
- **偷换票房**：卖 A 记 B、截留票款、结构票价、线上销量未入系统

输出每日**可疑影院清单**与**可疑场次清单**，每条都带"为什么可疑"的人话说明和核查建议。

零第三方依赖（仅标准库），适合监管内网/离线部署。

---

## 快速开始

```bash
# 1) 生成含已知作弊样本的合成数据（含节假日/首映/合法包场等对照）
python3 -m boxoffice_audit.cli synth --out ./data --days 60 --cinemas 40

# 2) 运行某一天的检测，输出报告
python3 -m boxoffice_audit.cli run --data ./data --date 2026-09-15 --out ./out

# 3) 端到端自检：召回率 / 误报率
python3 -m boxoffice_audit.cli selftest

# 4) 单元测试
python3 -m unittest discover -s tests -v
```

产物（`./out/`）：

| 文件 | 用途 |
|---|---|
| `daily_report_YYYYMMDD.md` | 监管日报：总体概况 + 影院清单 + 场次明细 + 逐条说明 |
| `cinema_risk_YYYYMMDD.csv` | 可疑影院清单（可导入 Excel / BI） |
| `findings_YYYYMMDD.csv` | 可疑条目明细（含规则码、理由、核查建议） |
| `findings_YYYYMMDD.json` | 结构化结果（供下游系统/入库） |
| `run_stats.json` | 各阶段耗时与数据量 |

## 核心设计：如何不把"正常的异常"当成"异常"

这是本方案最关键的部分。节假日高峰、首映零点场、合法包场/团购在
**行为特征上和刷票高度相似**，直接设固定阈值必然大面积误报。
系统的应对是四层：

### 1. 上下文分层（`calendar_ctx.py`）

每条基线都在同一 **（日期类型 × 时段桶 × 影厅层级）** 分层内比较：

- **日期类型**：法定节假日 / 普通周末 / 调休上班日 / 平日。节假日用节假日自己的基线。
- **时段桶**：19:00 黄金场和 03:00 凌晨场的正常上座率本就不同，不能混比。
- **影厅层级**：IMAX/杜比等特效厅上座率天然偏高，单独成层。
- **影片生命周期**：首映日零点场是正常高峰，单独标记。

### 2. 稳健统计（`baseline.py`）

- 用**中位数 / MAD**（中位绝对偏差）而非均值/标准差：刷票房本身会污染均值和方差。
- 小样本向全局**收缩**（shrinkage），避免小影院、冷门时段的随机噪声造成误报。
- 基线统计在建库时**一次性预计算**，评分 O(1)，支撑全国日批的时效要求。

### 3. 主证据 / 支撑证据两级规则（`config.py`）

- **主证据**（可单独定罪）：深夜异常上座、售票时间高度集中、异常低价、锁场退票、
  排片与上报影片不符、线上缺口、结构票价。
- **支撑证据**（只能加分）：满座、单设备占比高、连座大额、非会员匿名、柜台占比高。

> 为什么这样分："满座"和"一台设备买很多票"在正常经营里非常常见（包场、热门场次）。
> 如果让它们单独成案，清单会被淹没。**只有出现主证据，条目才进入清单。**

### 4. 误报抑制（mitigator）

命中以下情形对可疑度**打折**，并在结果中注明：

| 代码 | 含义 | 触发条件 |
|---|---|---|
| M01 | 节假日基线调整 | 当日为法定节假日/档期 |
| M02 | 首映零点场 | 上映当天凌晨场次 |
| M03 | 疑似正常包场/团购 | 团体渠道占比高 + 提前预订 + 无异常折扣 |
| M04 | 热门特效厅 | IMAX/杜比等 |
| M05 | 影片级异常（非影院个例） | 同城多家影院同片同时异常 |

此外，**设备集中度计算排除团体/包场渠道**——包场天然是一个买家一台设备，
把它算进去会造成系统性误判。

## 检测规则一览

### 虚假票房（F）

| 代码 | 名称 | 主/支撑 | 说明 |
|---|---|---|---|
| F01 | 深夜场次异常上座 | 主 | 深夜场上座率显著高于同层影院历史基线（稳健 z） |
| F02 | 满座异常 | 支撑 | 上座接近 100%，需其他证据配合 |
| F03 | 设备/账号高度集中 | 支撑 | 少数设备购买大部分票（已排除团体渠道） |
| F04 | 售票时间高度集中 | 主 | 绝大多数票在开场前 10 分钟内售出（机器下单特征） |
| F05 | 异常低价票 | 主 | 均价远低于同城最低结算价（1 元票刷量） |
| F06 | 非会员匿名购票 | 支撑 | 高上座场次几乎全为非会员 |
| F07 | 锁场后退票 | 主 | 开场前集中占座、临近开场大量退票 |
| F08 | 整排连座购买 | 支撑 | 单笔大额连座 |

### 偷换票房（D）

| 代码 | 名称 | 主/支撑 | 说明 |
|---|---|---|---|
| D01 | 排片与上报影片不一致 | 主 | 同场次排片影片 ≠ 结算上报影片（最直接证据） |
| D02 | 冷门片场均异常 | 主 | 冷门片上座率远高于同城同片（票房被转移进来） |
| D03 | 热门片份额被压低 | 支撑 | 热门片份额显著低于同城同档 |
| D04 | 线上销量与上报缺口 | 主 | 线上售票量 > 影院上报票量（按影片 + 影院日双重对账） |
| D05 | 票价结构异常 | 主 | 上报结算价远低于观众实付（阴阳票价） |
| D06 | 柜台渠道占比异常 | 支撑 | 柜台售票占比远高于同城（偷换高发渠道） |

评分：`score = min(1, Σ证据权重 × 0.8^降权数)`，分高/中/低三级。

## 输入数据格式

放在同一目录，用 CSV（UTF-8/GBK 均可，支持中文或英文表头）。
**可空列缺失不会报错，坏行会被拒收并计数，不会中断批处理。**

| 文件 | 必需 | 关键列 |
|---|---|---|
| `cinemas.csv` | 是 | 影院编码、影院名称、城市、（城市等级） |
| `films.csv` | 是 | 影片编码、影片名称、上映日期 |
| `halls.csv` | 否 | 影厅编码、影院编码、影厅格式、座位数 |
| `showtimes.csv` | 是 | 场次编码、影院编码、影片编码、影厅编码、开场时间、可售座位数、结算票价 |
| `orders.csv` | 是 | 订单号、场次编码、渠道、票数、单价、下单时间、设备号、是否会员、状态、退票时间 |
| `settlements.csv` | 推荐 | 影院编码、场次编码、**上报影片编码**、上报人次、上报票房、上报均价 |
| `online_sales.csv` | 推荐 | 影院编码、影片编码、日期、线上人次 |
| `calendar.csv` | 推荐 | 日期、日期类型（holiday/weekend/workday/normal）、节假日名称 |

> `settlements.csv` 的 **上报影片编码**（filed_film_id）是识别"卖 A 记 B"的关键，
> 它记录影院在结算系统里把钱记到了哪部影片名下。缺失时该规则（D01）自动跳过。

列名别名映射见 `boxoffice_audit/schema.py`，可按实际数据格式扩展。

## 规模与时效

在一台普通机器（单核）实测：

| 数据规模 | 场次 | 订单 | 耗时 |
|---|---|---|---|
| 40 影院 × 60 天 | 6.1 万 | 101 万 | **6.4 秒** |
| 2000 影院 × 3 天（≈3.8 万银幕） | 14.6 万 | 204 万 | **14.5 秒** |

全国日批（约 4 万银幕，25 万场次/天，~400 万订单）预计半分钟级，
远在"次日 12:00 前出清单"的时限内。架构上可按影院/城市分片并行扩展。

## 自检与调参

```bash
python3 -m boxoffice_audit.cli selftest
```

在 60 天 × 40 影院的合成数据上（含 145 例假票房、158 例偷换、28 例合法包场对照）：

```
假票房召回率      : 100.0%
偷换票房召回率    : 97.5%
合法样本误报率    : 7.1%
清单精确率(近似)  : 94.0%
```

所有阈值集中在 `boxoffice_audit/config.py` 的 `DetectorConfig`，
上线前应拿**真实标注数据**回测后调参，而非直接使用合成数据的最优值。

```

│   └── diversion.py       偷换票房检测

├── synth/generate.py  合成数据生成（含注入与合法对照）
└── cli.py             命令行入口
```

## 已知局限与后续方向

1. **依赖上报影片字段**：D01 需要结算数据里带"上报影片编码"。若监管方只能拿到
   汇总票房而无场次级结算明细，需改用 D02/D03/D04 等间接证据。
2. **包场识别是启发式**：真实包场合同数据若可得，应作为白名单输入，进一步降低误报。
3. **是否需要更细的团伙识别**：当前按设备/账号聚合，未做跨场次的购票团伙图分析，
   可作为下一步增强（同一批设备在多家影院批量购票）。
4. **阈值为合成数据标定**：上线前必须用真实标注数据回测，特别是各城市、
   各院线的票价分布差异较大，宜按城市/院线分别标定。
